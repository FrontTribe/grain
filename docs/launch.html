00 Why grain wins on HN

Grain is unusually well-suited to Hacker News, and the launch should lean into exactly that:

  • Culturally charged, right now. "How much of this code is AI?" is a live, unresolved debate. HN will have opinions — which means comments, which means the front page.
  • Developer-native. It's a Go CLI you run in your own repo in one command. No signup to try. HN rewards "I can run this in 10 seconds."
  • Self-distributing. The README badge is an ad on every repo that adopts it.
  • Honest by construction. "Signals, not verdicts" and openly-stated limits are catnip for a skeptical audience. The honesty is the pitch.
The one risk to manage
HN's reflex will be "another AI-detector that will falsely accuse people." You defuse this by raising it yourself, first, in the comment — before anyone else does. Own the limitation and you convert the biggest objection into a trust signal.

01 Timing

  • Day: Tuesday, Wednesday, or Thursday. Avoid Friday–Sunday (lower weekday-dev traffic) and Monday (inbox chaos).
  • Time: ~08:00–10:00 US Eastern. Catches the US morning and European afternoon in one window — grain's core audience.
  • One shot: post once. If it doesn't catch, you may repost once after a substantial change, weeks later (HN allows a second Show HN for a real update). Don't spam reposts.
  • Be free for 6 hours after. The first two hours decide everything; you must reply fast. Don't launch and walk away.
Rule
Never ask for upvotes, never post the link in group chats asking friends to vote — HN detects voting rings and will bury you. Let it rise on its own.

02 The title

Primary — use this
Show HN: Grain – see how much of your codebase was written by AI vs humans

Concrete, instantly clear, mildly provocative, zero buzzwords. The reader knows exactly what it does before clicking.

Backups (if you want a different angle)

  • Show HN: Grain – a provenance layer that labels AI-assisted code in your repo
  • Show HN: I built a "nutrition label" for AI vs human code in Git
Title rules
No "revolutionary", no "AI-powered", no emoji in the HN title. Say what it does, not how it feels. The URL should point straight at the GitHub repo (not the marketing site) — HN prefers the source.

03 The first comment

Post this as the first comment immediately after submitting (from your own account). It's the single most important asset of the launch — it frames the whole thread. Draft:

first comment — paste as-is, tweak the repo URL
Hi HN. I built Grain because two things collided this year: AI agents now commit directly to repos, and maintainers have started rewriting their contribution policies to ask "what did an AI write here?" There was no neutral way to actually measure that, so I made one. Grain reads your git history and reports how much of a repo is human-written vs AI-assisted, with a confidence level on every claim. One command: npx grain scan It writes a PROVENANCE.md, a grain.json, and a README badge. A GitHub Action posts a calm, itemized comment on each PR. The core principle is "signals, not verdicts," and it is NOT an AI-cheating detector — I've worked hard to keep it from becoming one: - Declared signals (Co-Authored-By trailers, bot accounts, explicit tags) are high-confidence. Behavioral inference (diff shape, burst timing) is deliberately weak and capped at 0.70 confidence — it never claims certainty from a guess. - It can be defeated by stripping a trailer. That's fine: it's a transparency tool for cooperative repos, not an anti-cheat. I say so in the README, because overclaiming is exactly what would make a tool like this harmful. - The whole engine is dependency-free Go and runs locally — your code never leaves your machine. MIT licensed. Honest dogfood: Grain scans its own repo as 100% AI-assisted, because every commit is Co-Authored-By Claude. It doesn't pretend otherwise. Two things I'd genuinely love feedback on: (1) does the behavioral-inference layer earn its place, or should it be declared-signals-only? (2) as a maintainer, what would make the PR comment useful instead of noise? Repo: github.com/FrontTribe/grain — happy to answer anything.
Why this works
It's personal (why you built it), concrete (one command), and it raises the two biggest objections — "it'll falsely accuse people" and "it can be gamed" — before the crowd does, then answers them. Ending on two real questions invites discussion instead of applause.

Do all of this the day before. On launch morning you only hit submit.

  • README opens strongFirst screen: one-line what-it-is, the npx grain scan command, and the example output. HN reads the README, not the site.
  • The install path actually worksTest npx grain / go install on a clean machine. A broken first command kills the launch. If npx isn't wired yet, lead the README with go install or a curl script.
  • Grain badge on grain's own READMEDogfood is the demo. The 100%-AI badge on your own repo is a great, honest talking point.
  • Demo GIF embedded in the READMEA 20–30s asciinema/GIF of grain scan. See §05.

05 Demo assets

Two visuals do 90% of the work. Prepare both before launch:

  1. A terminal recording of grain scan (20–30s). Use asciinema (crisp, copy-pasteable) or a GIF via vhs. Show: the command, the bars filling, "wrote PROVENANCE.md", then grain explain <sha> revealing the Co-Authored-By signal. End on the honest 100%-AI dogfood.
  2. A screenshot of the PR comment from the GitHub Action on a real PR (you already have one on PR #1). It shows the product in its natural habitat.
Keep it real
Don't stage a fake "73% human" repo for the demo. The 100%-AI dogfood is more memorable and more credible because it's honest — that's the whole brand.

06 Objection FAQ — prepared answers

These are the comments you will get. Reply fast, agree where they're right, never get defensive.

Q"This is just heuristics — it can be trivially gamed."
ACorrect, and it's in the README. Grain is a transparency tool for cooperative repos, not an anti-cheat. Declared signals (Co-Authored-By, bot commits) carry the weight; inference is a weak, capped hint. If someone wants to hide AI use they can — grain measures the honest signal that exists, it doesn't claim to catch adversaries.
Q"False positives will flame innocent developers."
AThat's the failure mode I designed hardest against. Inference confidence is capped at 0.70 and always labeled "inferred"; the output says "62% of lines carry AI signals," never "this person cheated"; and the default is comment-only, never a merge block. A human who writes clean code reads as human unless there's a declared signal.
Q"This will be used by managers to surveil/punish devs."
AA real risk, and an explicit non-goal. Grain is framed for maintainer transparency, not dev policing; there's no per-developer leaderboard, and the copy avoids blame language. I'd rather it be less "powerful" than become a weapon — that's a deliberate product choice, not an oversight.
Q"Why not just grep for Co-Authored-By?"
AThat's exactly grain's highest-confidence signal — grain just aggregates it across the whole history, weights by lines, renders a badge + PR comment + PROVENANCE.md, adds CODEOWNERS-aware policy, and falls back to (clearly-labeled) inference when the trailer is absent. The grep is the seed; the product is everything around it.
Q"GitHub will just build this in."
AMaybe. If they ship declared-signal counting, great — that validates the need. The defensible part isn't the counter; it's owning the norm early, plus the org policy engine and the compliance/audit layer (EU AI Act, signed provenance) where the actual budgets are.
Q"Who even cares what % is AI? AI-assisted isn't bad."
AAgreed — grain is neutral, not a purity test. The people who care are already telling us: maintainers rewriting contribution policies, and orgs facing provenance/disclosure requirements (EU AI Act). Grain is for them; if you don't need it, the badge is opt-in.
Q"Your own repo is 100% AI — isn't that embarrassing?"
AIt's the honest result and I lead with it. Every commit is Co-Authored-By Claude, so grain reports 100% AI-assisted. A provenance tool that fudged its own number would be worthless — the dogfood being unflattering is the point.

07 Launch-day conduct

  • Reply to everything in the first 2 hours. Speed and presence signal a real, engaged maintainer. This is the whole game.
  • Thank critics specifically. "Good point — you're right that X" earns more trust than any defense. Upvotes follow humility.
  • Never argue or get defensive. If someone's hostile, answer the substance calmly or don't answer. Don't feed flame.
  • Ship a small fix live. If a good suggestion lands, do it that day and reply "done — thanks, shipped in <commit>." Nothing converts a thread like visible responsiveness.
  • Don't touch the votes. No asking, no rings, no sockpuppets. Ever.

08 After the front page

Day 0, evening

Harvest the feedback

Collect every concrete suggestion and objection into GitHub issues. The thread is a free product-research session.

Day 1–2

Ship the top ask

Pick the single most-requested improvement and ship it. Reply in the (still-live) thread that you did.

Day 2–3

Thank-you + recap

A short post/tweet: "Show HN takeaways + what I shipped from your feedback." Keeps momentum and shows you listen.

Week 1

Convert interest

Point Cloud-curious commenters at the waitlist. Note which objection recurred most — that's your next roadmap item.
